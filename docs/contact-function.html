Contact form function

How the contact form on moiraemoss.com delivers mail to contact@moiraemoss.com, and how to deploy it.

How it works

The site is a static export on GitHub Pages, so the form cannot send mail by itself. When a visitor submits the form on /contact, the browser posts the fields as JSON to a Scaleway Serverless Function. The function checks the request and sends one email through the SMTP relay of Scaleway Transactional Email (TEM), smtp.tem.scaleway.com, on port 465 with implicit TLS.

  • From: Moirae Moss website <website@moiraemoss.com>. moiraemoss.com is a verified TEM domain with SPF and DKIM published.
  • To: contact@moiraemoss.com.
  • Subject: Website enquiry - <first name> <last name>.
  • Reply-To: the visitor's address, so replying in the mail client answers the visitor directly.

The code lives in functions/contact/:

FileRole
handler.jsThe entry point Scaleway calls (handler.handle). It builds the SMTP transport with Nodemailer from the function's environment.
contact.jsEverything else: CORS, rate limit, parsing, validation, the honeypot and the message itself. The sender is passed in, so it is tested without a network.
contract.jsField length limits and the honeypot field name. The site's form imports the same module, so the browser and the function enforce the same limits.
contact.test.jsUnit tests (pnpm test, also run in CI).
deploy.shCreates or updates the Scaleway namespace and function, sets its secrets, uploads the code and prints the endpoint.

The form reads the endpoint from NEXT_PUBLIC_CONTACT_ENDPOINT, which is inlined when the site is built. If the variable is unset or empty at build time, the form falls back to opening a mailto: link to SITE.email in the visitor's own mail app, so a local build without the variable still works.

Request and response

POST with Content-Type: application/json, carrying firstName, lastName, email, message and the honeypot field website, which must be empty.

StatusBodyWhen
200{"ok":true,"id":"<Message-ID>"}The TEM relay accepted the email for contact@moiraemoss.com.
200{"ok":true}The honeypot was filled. Nothing is sent, and the bot is not told.
204emptyCORS preflight from an allowed origin.
400{"ok":false,"error":"invalid_fields","fields":[...]}A field is missing, too long, has control characters, or the email is not address-shaped. Also malformed_body for bad JSON.
403{"ok":false,"error":"origin_not_allowed"}The Origin header is missing or not allowed.
405{"ok":false,"error":"method_not_allowed"}Any method other than POST or OPTIONS.
413{"ok":false,"error":"payload_too_large"}Body over 32 KiB.
415{"ok":false,"error":"unsupported_media_type"}Any other content type.
429{"ok":false,"error":"rate_limited"} with Retry-AfterMore than 5 posts from one IP in 10 minutes.
500{"ok":false,"error":"not_configured"}The SMTP username or password is not set on the function.
502{"ok":false,"error":"send_failed"}The relay refused the email or could not be reached in time. The reason is written to the function's logs, not returned.

The only allowed origin is https://moiraemoss.com.

Field limits: first and last name 100 characters each, email 254, message 5000.

Rate limit

The limiter keys each request on the last entry of the X-Forwarded-For header, which is the address the Scaleway platform appends. Observed against the deployed function on 2026-09-22: Scaleway keeps any X-Forwarded-For value the client sends as the leading entries and appends the real client address after them, so the first entry is attacker-controlled and only the last one can be trusted. In that probe, posts with an invalid body from one client hit 429 after 5; the same client sending a fresh forged leading value on every request was, with the first entry as the key, never limited. The unit tests cover the same case: a different forged leading entry on each request still counts against the real address.

The per-IP rate limit is kept in memory inside each function instance. It resets when an instance scales to zero after being idle, and each instance keeps its own count (the function scales to at most 2 instances). That is enough to stop one client from flooding the inbox in a burst, but it is not a durable quota. If spam gets through, add a challenge such as Cloudflare Turnstile (see follow-ups).

Secrets and configuration

No secret is in the repository. The function sends with the existing Scaleway IAM application stalwart-smtp, whose only permission is TransactionalEmailEmailSmtpCreate. deploy.sh sets these variables on the function:

VariableKindValue
TEM_SMTP_USERNAMEplainThe Project ID that owns the moiraemoss.com TEM domain. It is public anyway: it is the DKIM selector in DNS.
TEM_SMTP_PASSWORDsecretThe secret key of stalwart-smtp.

The relay host and port are fixed in handler.js: smtp.tem.scaleway.com on 465 with implicit TLS.

The deploy script reads its inputs from an env file kept outside every repository, mode 0600, at ~/.config/scaleway/moiraemoss-contact-form.env:

SCW_DEFAULT_PROJECT_ID=...
SCW_DEFAULT_ORGANIZATION_ID=... # optional, defaults to the project id
SCW_DEFAULT_REGION=fr-par
SCW_DEPLOY_ACCESS_KEY=...   # IAM application with FunctionsFullAccess only
SCW_DEPLOY_SECRET_KEY=...
SCW_TEM_SMTP_PASSWORD=...   # secret key of the stalwart-smtp IAM application

The CLI needs an organization id. When the file does not set one, the script uses the project id, which is the organization id when the project is the organization's default project.

The script deploys with the deploy key only. It points SCW_CONFIG_PATH at an empty temporary path, so any other Scaleway profile on the machine is ignored.

Deploy and redeploy

You need the Scaleway CLI (scw, v2.62 or later), jq, zip and npm on PATH. The same command does the first deploy and every redeploy:

functions/contact/deploy.sh ~/.config/scaleway/moiraemoss-contact-form.env

It is safe to run again. Each run:

  1. Finds or creates the moiraemoss function namespace in the project, and waits for it to be ready.
  2. Finds or creates the contact function, and sets its runtime (node24), handler, scaling (0 to 2 instances, 128 MB, 20 s timeout), public access, HTTPS redirect and SMTP credentials.
  3. Copies the function's files to a temporary directory, installs its production dependencies from package-lock.json, zips the result with node_modules, uploads it and deploys it.
  4. Prints the function status and its public endpoint, https://<id>.functions.fnc.fr-par.scw.cloud.

To rotate the SMTP password, create a new API key for stalwart-smtp, put its secret in the env file, run the script again, then delete the old key. Anything else that uses stalwart-smtp needs the new key too.

Point the site at the function

The site build reads the endpoint from the GitHub repository variable NEXT_PUBLIC_CONTACT_ENDPOINT (a variable, not a secret, because the URL is public in the built JavaScript anyway). Set it once, then rebuild the site:

gh variable set NEXT_PUBLIC_CONTACT_ENDPOINT --body "https://<id>.functions.fnc.fr-par.scw.cloud"
gh workflow run deploy.yml

For a local build, put the same line in .env.local (see .env.example). The function accepts only the https://moiraemoss.com origin, so a browser on localhost cannot post to the deployed function. Exercise the function locally through its unit tests or a local harness such as the Scaleway function emulator, not through the live function.

Checking it works

curl -sS -X POST "$ENDPOINT" \
  -H 'Origin: https://moiraemoss.com' \
  -H 'Content-Type: application/json' \
  -d '{"firstName":"Test","lastName":"Message","email":"you@example.com","message":"Test from the deploy doc."}'

A {"ok":true,"id":"..."} reply means the TEM relay accepted the email. Delivery is confirmed only when the message arrives in the contact@moiraemoss.com mailbox. The TEM section of the Scaleway console shows each email's status (new, sending, sent, failed), and the function's logs show the relay's reply for every send and the reason for every rejection.
